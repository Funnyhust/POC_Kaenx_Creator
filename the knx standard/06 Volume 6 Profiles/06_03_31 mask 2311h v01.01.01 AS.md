**Individual Address**

This device only has one single IA – named the cEMI Server IA – and it will defend this as specified
in [01] (clause 4.6.7.3.2 “Defending the cEMI Server IA”). This IA is exclusively stored in
PID_CEMI_SERVER_SNA and PID_CEMI_SERVER_DEVICE_ADDRESS in the cEMI Server
Object.


This IA shall be readable and writeable over the cEMI services for local management. As there is no
Transport Layer, this IA is not directly readable or writeable from the bus using the cEMI Server IA: the
TL-services needed to this will either be ignored, or will be passed to the cEMI Client. In the same way,
mask 2311h does not require any Application Layer or Management. It shall thus not be possible to
modify the cEMI Server IA through A_IndividualAddress_Write.

**Device Descriptor**


Mask 2311h shall have a Device Descriptor Type 0 with value 2311h. This shall however only be
accessible over the USB interface using the USB “Feature 02: Host Device Device Descriptor Type 0”.

   - This DD0 shall not be stored in any Property.

   - Consequently and additionally, this DD0 shall thus not be accessible through the cEMI services
for local management, neither through any service from the bus.

   - Specifically, as mask 2311h shall not have any management, this DD0 shall not be readable
through the service A_DeviceDescriptor_Read from the bus.

**Data Link Layer (Layer 2)**

The USB interface (mask 2311) and mask n will share the same bus connection, but will have different
Individual Addresses.

- If the USB connection is closed, then the Data Link Layer of the device will behave as the Data Link
Layer of mask n.

- If the USB connection is open, then this behaviour (accepting Frames, passing and possibly
acknowledging) will be extended with the Data Link Layer behaviour of the USB interface, in
function of the Property Filtering Mode Selection (PID_FILTERING_MODE_SELECT).

**cEMI Transport Layer**

- The MaC shall discover whether or not the cEMI Transport Layer is supported by reading and
evaluating the mandatory PID_COMM_MODES_SUPPORTED ([01]).

- The cEMI Transport Layer is mandatory if local device management is supported (see [04] clause
“Level 3 EMI: protocol and device management”).

   - If it is available, then the end device can be downloaded locally via the cEMI Transport Layer.

This has the advantage that there will be no communication on the bus. While the cEMI
Transport layer is enabled, the end device, “mask n” shall assume an open Transport Layer
connection and shall refuse any further requests for opening a Transport Layer connection
(see clause 3.5.4.2 in [05]).

This benefits from the communication speed of USB. It is not limited to the
communication speed on the bus, but profits from the USB communication speed. As there
are no Transport Layer confirmations either, fewer messages are needed. Additionally, as
there is no communication over air, the configuration is not received by any other
participant, making eavesdropping of the configuration impossible.

   - If the cEMI Transport Layer is not implemented, then the MaC (cEMI Client) shall not attempt
to manage the end device part.

This would in theory still be possible by connecting to the cEMI Data Link Layer and
sending point-to-point messages to the IA of the end device.

This has, amongst other, the disadvantage that Frames will be sent on the KNX medium.

Additionally, this is limited to the communication speed and timing of the KNX
communication medium.

Therefore, local device management is only allowed through the cEMI Transport Layer.

**Individual Addresses**

This device will have two Individual Addresses.
1. The cEMI Server IA, as specified above without any change.

This cEMI Server IA can thus not be changed over the bus using Programming Mode or
accessing the Properties PID_SUBNET_ADDR or PID_DEVICE_ADDRESS targeted at
the cEMI Server IA.

However, these Properties can be accessed over the bus accessing these Properties
addressing the IA of mask n!

2. The IA of mask n, stored in PID_SUBNET_ADDR and PID_DEVICE_ADDR of the Device Object.


-----

**Device Descriptor**

There will be two DD0–values.
1. Mask 2311h as specified above without change.
2. The mask version of mask n.

   - Over the cEMI connection, this may be retrieved through PID_DEVICE_DESCRIPTOR in the
Device Object or through other means, like A_DeviceDescriptor_Read applied using cEMI TL
services.

   - Over the bus, this Device Descriptor can be accessed without restriction, using the
A_DeviceDescriptor_Read-service addressed to the mask n IA. If this service is addressed to the
cEMI Server IA, then it will either not be responded, or it will be passed to the cEMI Client.

### 2 Constraints
**No Remote Configuration**

Mask 2311h does not foresee any Remote Network – or Device Configuration. It is not possible to change
the DoA or IA over the network via any (system) broadcast service. Additionally, it is not foreseen that
the Properties for DoA or IA can be accessed from the bus, neither any other Property or MaS
functionality (like an AP download). If anything of this is needed, then instead this mask 2311h shall be
implemented in combination with another mask version in the same device

**Can only be combined with one single additional Profile**

The below introduced mask 2311h for the KNX RF USB interface is designed to allow to be combined
also in a device in combination with another mask n. Mask 2311h itself does not have an own
Management as an end device; the possible management concerns the management of the mask n. This in
turn means that it is not possible to have more than one mask n in combination with mask 2311h, as the
cEMI Transport Layer does not allow to direct the cEMI TL-services to any instance of a management.
This may be solved in the future by firstly selecting the instance of the management that shall be
addressed by the cEMI TL messages.

NOTE 1 As for the access from the bus, these different masks or management instances would have different Individual
Addresses and could be addressed specifically. Over this access method, mask 2311h could effectively be combined with more
than one mask n instance and be configured.

### 3 Profile introduction
The Profile for mask 2311h is specified in [04]. This complies with the following general requirements.

The USB RF Interface 1.1 shall support the cEMI protocol as External Message Interface as specified
in [03]. It shall support the “L_Data services for KNX RF asynchronous Frames”.

In transmission direction, L_Data.req, the USB RF Interface 1.1 shall use the DoA or KNX Serial
Number as indicated in [03] (clause 4.1.5.1 “L_Data services for KNX RF asynchronous frames” and
specifically clause 4.1.4.3.2 “RF medium information”).

NOTE 2 This requires that if the cEMI Client sets the field LFN to the value 255, that then the cEMI Server uses its own LFN.
This is noted here, as it will be the typical use case by ETS.

In reception direction, the KNX USB RF Interface 1.1 shall set all the fields, such as SB, RF-‘SN’, LFN,
RF-‘info’ (with signal strength), according the received KNX RF Telegram contents.

DoA filtering is mandatory. It is required for an, RF interface to be able to receive all Telegrams on all DoA
for Bus monitoring purposes for example. The normal use should be to filter on the single DoA of the
interface.

The SB (System Broadcast) in the cEMI will reflect the AET (with Serial Number SB-flag = AET = 0)
System Broadcast and (with Domain Address SB-flag = AET = 1) Broadcast.
